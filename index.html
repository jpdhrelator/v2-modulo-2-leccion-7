Módulo 2 — Lección 07 — Actividad en clases

Versiona tu primer Portafolio con Git (local)

Vas a llevar un proyecto desde su primera línea de código hasta dejar un historial limpio, con ramas, etiquetas y resolución de conflictos. Todo ocurre en tu máquina, sin conexión a ningún repositorio remoto. No te entregaremos comandos: solo el qué; el cómo lo aprendiste en clases y está en la PPT y tus apuntes.

Contexto

Eres el desarrollador a cargo de armar el portafolio digital del equipo. Tu trabajo de hoy consiste en preparar el proyecto base y versionarlo correctamente en local con Git, aplicando todo el flujo visto en clases.

Habilidades que se evaluarán
  • Uso del terminal y configuración de Git
  • Flujo local: init, add, commit, status, log
  • Renombrado de archivos versionados y archivo .gitignore
  • Ramas, fusiones y resolución de conflictos
  • Recuperación de versiones anteriores
  • Etiquetado de versiones (tags)
  • Uso de stash para cambios temporales
  • Rebase para mantener el historial lineal
  • Documentación en Markdown
01
Prepara el terreno

Verifica que Git está instalado en tu equipo y que tu identidad de usuario está configurada de forma global con tu nombre real y un correo. Comprueba que la configuración quedó correctamente registrada.

Crea desde el terminal una carpeta llamada mi-portafolio dentro de tu directorio personal y entra en ella. Dentro, crea los siguientes archivos vacíos: index.html, estilos.css, script.js y notas.txt.

Verificación: al listar el contenido del directorio deben aparecer los cuatro archivos y al ejecutar la consulta de versión de Git debe responderte con un número de versión.
02
Abre la "caja" del proyecto

Inicializa el repositorio de Git dentro de mi-portafolio. Antes de hacer cualquier otra cosa, consulta el estado del repositorio y observa qué archivos aparecen y en qué color.

Agrega todos los archivos al área de preparación y realiza tu primer commit con un mensaje claro que diga: "Estructura inicial del portafolio".

Consulta nuevamente el estado y luego el historial de commits.

Verificación: el historial debe mostrar exactamente un commit, y el estado del repositorio debe estar limpio.
03
Trabaja en pequeños commits

Edita los archivos para darle algo de vida al portafolio:

  • En index.html escribe una estructura HTML mínima con tu nombre dentro de un <h1>.
  • En estilos.css define un color de fondo y un color de texto para el body.
  • En script.js deja un console.log con un saludo.

Realiza tres commits independientes, uno por cada archivo modificado, cada uno con su propio mensaje descriptivo. Al final, revisa el historial en formato resumido de una sola línea por commit.

Verificación: el historial debe mostrar cuatro commits en total. Cada mensaje debe describir lo que se cambió.
04
Renombra sin perder la historia

El archivo notas.txt debe llamarse TODO.md. Usa el comando de Git apropiado para que el cambio de nombre quede registrado como un renombre y no como una eliminación más una creación.

Confirma el cambio con un commit cuyo mensaje describa la operación.

Verificación: al revisar el estado antes del commit, Git debe identificar la operación como renamed. El historial del archivo debe seguir vivo bajo el nuevo nombre.
05
Define qué NO debe versionarse

Crea dentro del proyecto un archivo de configuración local llamado config.local (con cualquier contenido inventado) y una carpeta cache/ con un archivo dummy dentro.

Estos artefactos no deben formar parte nunca del historial del proyecto. Configura tu repositorio para que Git los ignore por completo. Si ya hubieran entrado al historial por error, asegúrate de que Git los olvide.

Realiza un commit con el archivo de exclusión.

Verificación: tras la configuración, el estado del repositorio debe estar limpio aunque modifiques config.local o agregues nuevos archivos a cache/.
06
Aísla tu trabajo en una rama

Crea una rama nueva llamada feature/seccion-contacto y posiciónate en ella. En esa rama, crea un nuevo archivo contacto.html con un formulario básico (al menos un input de email y un botón). Realiza el commit correspondiente.

Cambia de regreso a la rama principal y verifica que el archivo contacto.html no está presente. Vuelve a la rama de la feature y comprueba que sí está.

Verificación: al cambiar entre ramas, el archivo aparece y desaparece según corresponda.
07
Provoca y resuelve un conflicto

Estando en la rama principal, modifica la línea del <h1> de index.html para que diga "Portafolio de [tu nombre] — versión profesional". Commitea el cambio.

Cambia a la rama feature/seccion-contacto y modifica la misma línea del <h1> para que diga "Portafolio de [tu nombre] — versión creativa". Commitea.

Vuelve a la rama principal e intenta fusionar la rama de feature. Cuando Git te avise del conflicto, ábrelo, decide manualmente el contenido final (deja una versión que combine ambas ideas, por ejemplo "Portafolio profesional y creativo") y completa la fusión.

Cuando todo esté limpio, elimina la rama feature/seccion-contacto.

Verificación: el historial visualizado en modo gráfico debe mostrar el commit de fusión uniendo ambas ramas, y la rama de feature ya no debe existir.
08
Viaja en el tiempo

Tu cliente quiere ver cómo se veía index.html en su versión más antigua, pero sin perder el trabajo actual. Consulta el historial en formato resumido, identifica el hash del primer commit, y restaura solo el archivo index.html a esa versión inicial.

Confirma el cambio con un commit que indique la restauración. Verifica que el resto de los archivos (CSS, JS, etc.) siguen en su versión actual.

Verificación: el contenido de index.html es el del primer commit y el historial del proyecto no se ha reescrito (todos los commits anteriores siguen ahí más el nuevo).
09
Marca un hito

Tu portafolio acaba de alcanzar su primera versión estable. Marca el commit actual con una etiqueta anotada llamada v1.0 y un mensaje que diga "Primera versión estable del portafolio".

Crea también una etiqueta ligera v1.0-demo sobre el mismo commit para diferenciar el uso de ambos tipos.

Consulta el detalle de la etiqueta anotada y verifica que aparezcan autor, fecha y mensaje.

Verificación: al listar las etiquetas deben aparecer ambas, y el detalle de la anotada debe mostrar autor, fecha y mensaje.
10
Guarda el avance, atiende una urgencia, retómalo

Empieza a editar estilos.css agregando estilos para un futuro menú de navegación, pero no hagas commit. Comprueba que el archivo aparece como modificado.

De pronto, te avisan de un bug urgente: en script.js el console.log tiene un error tipográfico. Guarda tu trabajo en curso de los estilos en un "cajón temporal" para que tu directorio quede limpio, corrige el console.log, commitea esa corrección, y luego recupera tu trabajo de estilos para seguir donde lo dejaste.

Cuando termines los estilos, commitea normalmente.

Verificación: el listado del cajón temporal debe quedar vacío al final, y el historial debe contener tanto la corrección del bug como la nueva versión de los estilos.
11
Mantén el historial lineal con rebase

Crea una nueva rama llamada feature/footer a partir de la rama principal. En ella, realiza dos commits: el primero agrega un <footer> a index.html con tu nombre y el año; el segundo agrega estilos para ese footer en estilos.css.

Cambia a la rama principal y realiza un commit independiente: agrega en TODO.md una lista con dos próximas tareas que harías al portafolio.

Vuelve a la rama feature/footer y, en lugar de fusionar con merge, reorganiza sus commits para que queden colocados encima del último commit de la rama principal, dejando un historial lineal sin commit de merge.

Cuando termines, fusiona feature/footer en la rama principal y revisa el historial gráfico.

Verificación: el historial gráfico debe verse como una línea recta, sin bifurcaciones ni commit de merge. Los dos commits del footer deben aparecer después del commit de TODO.md.

Si durante el proceso aparecen conflictos, resuélvelos en los archivos, márcalos como resueltos y continúa el proceso.

12
Documenta tu proyecto en Markdown

Crea en tu proyecto un archivo README.md bien formateado en Markdown que incluya al menos:

  • Un título principal y una descripción breve del portafolio.
  • Una sección de Requisitos con una lista de viñetas.
  • Una sección de Estructura del proyecto en formato de tabla con los archivos principales y su propósito.
  • Un bloque de código mostrando cómo abrir index.html desde el navegador.
  • Una lista de tus datos de contacto.

Commitea el README. Ábrelo con el visualizador Markdown de tu editor (VS Code: clic derecho → "Open Preview") para validar que se renderiza con sus títulos, tabla y bloque de código.

Verificación: el archivo README.md está commiteado y al previsualizarlo se ve con jerarquía de títulos, tabla y bloque de código formateado.

Entrega

Al finalizar, comparte con tu profesor desde tu terminal:

  1. El historial completo de tu repositorio en formato gráfico, una línea por commit, mostrando ramas, fusiones y etiquetas (captura de pantalla).
  2. El resultado de listar todas tus etiquetas y el detalle de la etiqueta anotada.
  3. El contenido renderizado de tu README.md (captura del preview).
  4. El listado actual de tu cajón temporal (debe estar vacío).
